# Enabling the register cache: what was measured, and what was not

`REGCACHE_NONE` held until the evidence for every part of a cache existed:
readable and volatile predicates, a defaults table, and a way to prove on
hardware that the cache agrees with the chip. This records the enablement, the
runs that certify it, and — at least as important — the one question it does
not answer.

Evidence, all from one cold boot of `regcache-rc9` (pkgrel 144) on 2026-08-15:

| run | verdict |
|---|---|
| `wcd9320-coldboot-autoload-20260815T175343Z.txt` | PASS 31/0 |
| `wcd9320-regcache-20260815T175356Z.txt` | PASS 25/0 |
| `wcd9320-irq-acceptance-20260815T175409Z.txt` | PASS 27/0 |

## The configuration

Generated by `tools/wcd9320-gen-cache-tables.py` from
`wcd9320-fullmap-20260815T154307Z.txt`, and asserted against the built module's
ELF by `tools/wcd9320-verify-artifact.py`:

| table | count | derivation |
|---|---|---|
| `readable_reg` | 669 | 673 documented, minus 4 write-only `INTR_CLEAR`; 351 undocumented map holes rejected |
| `volatile_reg` | 401 | `taiko_volatile()` plus `0x1fd`, measured hardware-populated here |
| `reg_defaults` | 460 | every readable non-volatile register, including the 230 whose reset value is zero |

Both predicates are bitmaps rather than transcribed range logic: a slip in
hand-written ranges would be silent and intermittent, and `volatile_reg`
returns `true` for anything out of range so the fail-safe direction is a
wasted hardware read rather than a stale value.

### Why MAPLE and not FLAT

`regcache_flat_read()` always succeeds. A register absent from `reg_defaults`
reads back zero from the cache and never touches hardware, so any omission
becomes a silently wrong value forever. `regcache_maple_read()` returns
`-ENOENT` for an absent entry and the generic path falls through to a hardware
read, which makes an incomplete table a performance question instead of a
correctness one.

The table is not in fact incomplete — all 460 cacheable registers have an
entry, and the artefact gate asserts that `cacheable - defaults` is empty. The
choice is defence against a table that drifts later, not a workaround for one
that is wrong now.

Registering a zero is not the same as omitting it:
`regcache_reg_needs_sync()` skips a register only when its value equals a
registered default, so an absent entry is always synced.

### The bypass discipline

Every write-verification readback and both snapshot paths are wrapped in
`regcache_cache_bypass()`. Without it the core-init proof would report "all 15
steps applied cleanly" from values the cache echoed back, with nothing having
reached the codec. `wcd9320_snapshot_range()` is the single shared helper both
`snapshot_low` and `snapshot_cdc` route through, so the wrapping cannot drift
apart between them.

The other three readers — identity, IRQ state, MBHC — read only volatile
regions and reach hardware by the predicate, so they need no bypass. The
artefact gate counts relocations against `regcache_cache_bypass` and requires
exactly 10 call sites, five `true`/`false` pairs.

## What the hardware run proves

`tools/wcd9320-regcache-evidence.sh` reads every readable register twice —
once through the cache, once with the cache bypassed — and requires the pair to
be identical for every non-volatile register.

```
cacheable_checked=460 mismatches=0
volatile_checked=209 volatile_moved=0
read_errors=0
```

Because all 460 cacheable registers are preloaded from `reg_defaults`, that is
simultaneously a check of the cache **and** of the defaults table: a
mis-derived reset value would surface here as a mismatch against the live
codec. It did not, for any of them.

### The counts are part of the gate, deliberately

`mismatches=0` is trivially satisfiable by a run that checks nothing. A run
reporting `cacheable_checked=0` would look flawless and mean nothing — the same
shape of hole as the frozen `irq_observe` fields that made two acceptance
checks unfailable in `aa6feac`. So the run also asserts 460 / 209 / 669,
derived independently by parsing the module's ELF rather than from the driver's
report of itself.

### And a cache must actually exist

`cache_check` alone cannot establish that one does. Under `REGCACHE_NONE` every
`regmap_read` reaches the chip, so the cached read and the bypassed read are
the same read, `mismatches` is 0 for free, and `cacheable_checked` is still
460. A driver that had quietly lost its `cache_type` would produce a flawless
run.

regmap creates `cache_only`, `cache_dirty` and `cache_bypass` under debugfs
only when `cache_type != REGCACHE_NONE`, so the run asserts those files exist.
Measured present at `/sys/kernel/debug/regmap/217:a0:1:0`.

### The interrupt path is unaffected

The most dangerous part of the volatile predicate is the interrupt block, all
below `0x100` and all volatile. From the same boot, one physical headset
insertion still produced parent +1, child +1, post-ack status `00 00 00 00`,
quiescence on both counters, everything re-masked and `0x14a` restored — 27/0,
identical to the pre-cache runs.

## What this does NOT cover

**Volatility remains largely downstream's authority.** This run exercised the
MBHC path and the state the codec reached on one boot. Digital gain,
clip-detect, VBAT and the IIR/ANC coefficient windows have no stimulus here and
are marked volatile on `taiko_volatile()`, not on measurement. A register
wrongly marked volatile costs only a hardware read; the dangerous direction is
cacheable-when-it-should-not-be, and that is what the run measures — but only
over registers this boot actually moved. `volatile_moved=0` says nothing about
families nothing provoked.

**The adoption path is unexercised, and it is where `reg_defaults` could be
wrong.** `reg_defaults` describes the *reset* state. A regmap created against a
codec that something else already initialised would start out claiming reset
values while the hardware holds post-init ones, and nothing in the driver
reconciles the two — there is no `regcache_drop_region()`,
`regcache_sync()` or `regcache_mark_dirty()` call anywhere.

Six registers would be affected: `0x101`, `0x105`, `0x108`, `0x109`, `0x1fa`
and `0x311`, the core-init writes whose final value differs from `__POR`.
(`0x1fb` returns to its `__POR` of `0a`; the CDC defaults were taken from the
after-release stage and would match.)

**Neither available staging route reaches that state**, which is why this is
recorded as open rather than measured:

- `core_reinit` clears only the driver's software init state and re-enters the
  production decision function. It does not recreate the regmap, so the cache
  still holds what the driver wrote through it and reports `mismatches=0`
  without exercising the risk.
- `rmmod` + `modprobe` was tried on 2026-08-15. The re-probe could not verify
  identity (`identity_failures=3`, `stale_bus_state=1`), correctly declined to
  adopt, re-asserted reset (`reset_transitions` 2 → 3) and did a full fresh
  bring-up — `path=fresh adopted=0`. The cache was then populated against a
  genuinely reset codec and was correct by construction: `mismatches=0`.

  A prediction of 6 mismatches was made before that run and was wrong. What it
  actually established is that this route re-resets rather than adopts.

On this device the codec always comes up dark — `nonzero_before=0` on every
fresh boot ever recorded — and nothing else initialises it, so the condition is
**latent and currently unreachable** rather than a live defect. It becomes real
if something ever initialises the codec before this driver binds.

The fix, if it is ever needed, is small and is exactly the property MAPLE was
chosen for: drop the affected entries on the adoption branch so reads fall
through to hardware. `regcache_flat` could not do that.
